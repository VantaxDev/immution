## Remaining product limitations

1. This is log-based PHP application protection, not a general DoS firewall.
   It cannot stop network saturation, static requests or ordinary 200 floods.
2. Logs are processed after requests and use arrival-at-daemon time. Backlog
   can distort rate windows. Auto-discovery happens only at startup. IP-first
   Combined format is required; default virtual-host-prefixed logs are ignored.
3. State count, cache size, serialized writes and per-request event logging
   lack load-tested resource budgets. No throughput or CPU-saving claim is
   justified yet. A prolonged distributed scan needs stress measurements.
4. The ini conflict scan cannot establish absence of VirtualHost/.htaccess
   overrides. Mixed PHP versions and PHP-FPM need manual configuration review.
5. The report covers only active events.csv. Rotated files must be reviewed
   separately; event absence is not proof of detector coverage. Paths can
   contain personal data even after query/IP suppression.
6. Whitelist/exclusions apply to the PHP gate, not scoring. Shared NAT IPs and
   virtual hosts share a score. Legitimate admin/download routes can resemble
   probes. Googlebot is not authenticated.
7. Unblock serializes state removal, but a new suspicious request can score
   again. A PHP request that already read the old snapshot may still be denied.
8. Rollback intentionally leaves diagnostic snapshots and may leave a created
   service account or log directory. Backups need deliberate cleanup later.

Recommendation: run the updated CI, then use monitor mode on representative
traffic. Do not promote to stable based solely on this source review.
